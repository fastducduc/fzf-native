# fzf and fzf-native benchmark

Date: 2026-09-09T08:19:49Z

This report compares current upstream `fzf` with current `fzf-native` main.
The run includes real data, synthetic data, one-worker runs, eight-worker runs, and two independent holdout suites.

## Result

`fzf-native` won 6 of 19 steady-state match-list workloads.
It won all four dense all-match workloads by 1.21x to 1.31x.
It also won the Chromium workload by 1.13x.

`fzf` won 13 of 19 steady-state workloads.
It won rejection-heavy workloads by 1.68x to 2.21x.
It won the Arabic and Korean workloads by 1.36x and 1.26x.

The equal-weight geometric mean across all 19 workloads favors `fzf` by 1.31x.
This aggregate is a shape summary, not an estimate for an Emacs workload.

The first-query session lane favors `fzf` in all six cells.
The difference ranges from 1.01x on one-worker Chromium to 1.97x on eight-worker Korean.

## Limits

The direct comparison does not include a shared multi-round edit driver.
The two projects do not expose the same persistent-session interface.

The match-list lane excludes corpus ingestion and process startup.
The first-query lane excludes corpus ingestion but includes request publication and polling for `fzf-native`.

The session driver polls at intervals of up to 50 us.
The two worker pools use different schedulers and different orchestration code.

The `fuzzy-benches` holdout cannot call the unexported Go score function through the same C interface.
For this reason, the holdout reports only `fzf-native` values.

This run used one Apple M3 host.
It does not establish performance on x86-64, Linux, FreeBSD, or Windows.

The Rust build emitted a nonfatal warning because `rust-objcopy` did not find `libLLVM.dylib`.
The optimized benchmark executable built and ran successfully.
